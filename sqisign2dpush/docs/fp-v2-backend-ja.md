SQIsign2DPush の v2.0 型 Fp バックエンド

追記: [加算の carry 処理を統合した変更と、減算とのコスト比較](fp-add-fusion-ja.md)を追加した。以下の表は、その加算変更前の測定記録。

64-bit ref の内部表現を、未使用の上位 bit を残す limb（unsaturated limb）と `[0,2p)` の冗長 Montgomery 表現へ変更した。素数と数学的な演算は 2DPush のものを維持する。v2.0 のソースや定数をそのまま使う変更ではない。

**52・55・57 bit の決め方**

limb 数を `n`、幅を `w` とすると、配列の表す整数は `a[0] + a[1]·2^w + … + a[n−1]·2^(w(n−1))`、Montgomery 定数は `R = 2^(nw)` となる。機械の変数型は全レベルで `uint64_t`。`RADIX=64` は機械語・通常整数の幅、`FP_RADIX` は内部 Fp の limb 幅であり、別の値である。

| レベル | 素数 p | bit 長 | n | w | R | 1 bit 狭くした場合 |
|---|---|---:|---:|---:|---|---|
| lvl1 | 2^131·3^78−1 | 255 | 5 | 52 | 2^260 | 2^255 ≤ 4p |
| lvl3 | 2^191·3^117−1 | 377 | 7 | 55 | 2^385 | 2^378 ≤ 4p |
| lvl5 | 2^263·3^156−1 | 511 | 9 | 57 | 2^513 | 2^504 ≤ 4p |

今回は、5・7・9 limb という構成で `R > 4p` を満たす最小の整数幅を採用した。さらに、生成器の積和上界が `2^128` 未満であることと、実測の速度改善を確認した。この条件だけであらゆる CPU に対する最速の構成が一意に決まるわけではない。より広い幅や別の limb 数も候補にはなる。

v2.0 自体の 64-bit ref は 5×51、7×55、9×57 bit。v2.0 の lvl1 の素数は `5·2^248−1` で、2DPush の lvl1 より小さい。従って、v2.0 では 51 bit で足りても、2DPush では足りない。

**なぜ R > 4p なのか**

このバックエンドでは、乗算への入力 `a,b` を `[0,2p)` まで許す。その積 `T=ab` は `4p²` 未満。Montgomery 還元では `0 ≤ m < R` を選び、`u=(T+mp)/R` を計算するので、

`u < 4p²/R + p < 2p` （R > 4p）

となる。従って、乗算の最後に p を引いて `[0,p)` に戻す処理を省略できる。出力は次の演算にそのまま渡せる。これは今回の `[0,2p)` 契約に対する十分条件であり、Montgomery 演算一般で常に必要な条件という意味ではない。

**表現の二つの変更**

1. **limb に余裕を残す。** 従来の 64-bit limb では、64-bit 加算のあふれを別途検出し、次の limb へ渡す必要がある。新方式は 52/55/57 bit だけを使用するため、加算や減算の途中値と桁上がりを 64-bit 変数内で処理しやすい。乗算では例えば 57×57 bit の部分積を 128-bit 変数で蓄積する。部分積の個数、還元の項、桁上がりを含めた上界の確認も必要になる。
2. **p を法とする同じ値に複数の内部表現を許す。** 通常の値 x に対し `xR mod p`、およびそれに p を足した値を許す。加算・減算は 2p を境界として補正し、乗算・平方は `[0,2p)` に収まる還元を行う。limb 数が増えても、桁上がりと最終補正の削減で速くなる場合がある。

例えば p=7、R=32 の小さな例では、通常の値 x=3 は `3·32 mod 7=5` として格納でき、12 も同じ値の有効な内部表現である。通常の 0 には内部整数 0 と 7 が対応する。従って、配列のバイト比較だけでは等値・ゼロ判定はできない。

**本体との接続**

- `fp_backend.c` は生成済みの加減算、乗算、専用平方、Montgomery 変換を持つ。共有の API は `fp_backend.inc`。従来の `fp_hd256/384/512.c` は参照用に残し、ビルド対象から外した。
- 等値・ゼロ判定は正規化してから比較する。`fp_encode` は一意な通常整数の little-endian 表現へ変換する。デコードの長さは引き続き 32/48/64 bytes で、不正入力は戻り値・出力ともゼロ。
- `fp_decode_reduce` は任意長の little-endian 入力を扱う実装へ変更し、旧実装のブロック境界での還元範囲の問題も解消した。高速化の主対象ではないため、公開の入力長に比例する byte 単位の Horner 法を使っている。
- Fp のサイズは 40/56/72 bytes に増える。スカラーのサイズは `NWORDS_ORDER=4/6/8` を維持する。
- `fp_set_one` と `fp_set_small` は Montgomery 形式を直接返す。既存の `fp_set`、`fp_tomont`、`fp_frommont` は通常整数との変換用として残す。通常整数は従来の 64-bit 単位で格納し、Fp の配列サイズまでゼロで埋める。
- `fp_div3` は事前計算した 3 の逆元との乗算にした。固定指数コードは前回生成した手順を継続使用する。平方判定の binary GCD は通常整数へ変換してから実行する。
- 事前計算された Fp/Fp2 定数は、従来の Montgomery 表現の値を維持するよう新しい基数へ変換した。
- 署名と検証がハッシュしていた Fp2 のメモリ表現は、`fp_encode_legacy_hash` で従来の R による正規化済みのバイト列を明示的に作る。新しい配列のサイズや冗長表現に依存しない。既存の little-endian 実装のハッシュ入力を維持するための互換処理である。

v2.0 と API まで完全に同じではない。既存の呼び出し元に合わせ、`fp_is_equal`/`fp_is_zero`/`fp_is_square` は bool を返し、`fp_is_square(0)` は false とする。素数、符号化サイズ、署名方式も 2DPush のものを維持している。

**実測と再現**

変更直前の固定指数最適化済みの実装と、各チェックアウト自身のヘッダ・Montgomery 表現を使って比較した。GCC、`-O3 -funroll-loops -flto`、同じ通常値の入力、1 CPU に固定、測定順を入れ替えた 9 回の中央値。環境と全演算の値は [JSON](fp-v2-backend-results.json) に記録している。時間は ns/op、各欄は「変更前 → 変更後」。

| 演算 | lvl1 | lvl3 | lvl5 |
|---|---:|---:|---:|
| 加算 | 14.35 → 4.29 | 20.08 → 5.75 | 25.29 → 7.21 |
| 減算 | 10.90 → 4.16 | 15.25 → 5.22 | 19.69 → 6.82 |
| 乗算 | 24.91 → 16.07 | 55.13 → 27.45 | 105.49 → 42.87 |
| 平方 | 24.73 → 14.46 | 49.83 → 23.43 | 80.65 → 34.30 |

平方判定は通常整数への変換が加わるため、今回の測定では約 1–4% 遅くなった。表の改善率は演算単体のもので、署名全体の高速化率ではない。

```sh
python3 scripts/gen_fp_backend.py --check
python3 scripts/gen_fp_fixed.py --check
python3 scripts/test_fp_backend.py --repetitions 1000
python3 scripts/bench_fp_backend.py --baseline /path/to/old-checkout --output /tmp/fp-results.json
```

生成器は [Mike Scott の modarith](https://github.com/mcarrickscott/modarith/tree/dcdd51a3f49af0462d7a50f3bbdf63588c9f0cc0) の `monty.py` をライセンスとともに同梱した。指数生成・コンパイラ呼び出しの部分は実行せず、素数ごとの primitive の出力だけを使う。`fully_propagate=True` で演算の出力 limb に残る carry を伝播する。普通のビルドには Python や addchain は不要。

既存の飽和表現の定数を移行し直す場合は `scripts/convert_fp_precomp.py /path/to/old-checkout` を使う。この入力は旧 4/6/8-word 形式の別チェックアウトに限る。従来の Sage 事前計算スクリプトを直接実行して、新しい表現の定数を上書きしてはいけない。Sage の事前計算パイプライン全体の移行は今回の演算層の変更には含めていない。

検証: 全レベルの Python 整数オラクル（各 1,000 個の乱数・境界値・全入出力別名）、Fp/Fp2 テスト、鍵生成・署名・検証各 100 回を実行した。AddressSanitizer でも Fp/Fp2 と署名テストの 9 件がすべて成功した（`ASAN_OPTIONS=detect_leaks=0`、漏洩検査は対象外）。

Fp 加算の carry 処理の統合

`[0,2p)` の入出力範囲を維持したまま、加算のコード生成を変更した。対象は `scripts/gen_fp_backend.py` の `generate_add()` と、生成される全レベルの `modadd()`。減算や内部表現、符号化、事前計算定数は変更していない。

従来は配列へ和を書き、2p を引き、`prop()` で carry を伝播し、必要なら 2p を戻してもう一度 `prop()` を呼んでいた。新方式は、各 limb の「和・2p の減算・直前 limb の carry」を同じ式で計算する。戻し補正も同様に計算し、最後に出力を格納する。2p の補正そのものや、2 段階の carry 伝播を省略したわけではない。

下位 limb の特性を利用し、2p を `(-2, q1, q2, …)` と表す。上位の qi は 2p+2 の基数 2^FP_RADIX の各桁で、桁幅内に収める。全入力をローカル変数へ読み込んでから出力を書き始めるため、出力と入力が同じ配列でも正しく動作する。条件補正はマスクで行う。

この書き方は、コンパイラが中間値をレジスタへ置き、命令を並べる際の制約を減らす。効果はコンパイラと呼び出し方に依存するため、独立した入力での処理量と、前の出力に依存する連続加算を別々に測った。前者の改善だけを採用すると、連続加算を遅くする候補もあった。

**測定結果**

GCC 11.4、`-O3 -funroll-loops -flto`、1 CPU に固定。各ケース 300,000 回、31 ラウンドの測定順を入れ替え、中央値を採用。変更前は v2 型内部表現への移行後・今回の加算変更前のコード。両方のチェックアウトで同じ limb 幅を使用した。単位は ns/op。

| レベル | 独立入力の加算：前 → 後 | 変更後の減算 | 連続加算：前 → 後 | 変更後の連続減算 |
|---|---:|---:|---:|---:|
| lvl1 | 3.987 → 3.954 | 3.753 | 4.535 → 3.958 | 4.367 |
| lvl3 | 5.444 → 5.350 | 5.071 | 5.648 → 5.487 | 5.433 |
| lvl5 | 6.854 → 6.607 | 6.309 | 6.928 → 6.983 | 6.639 |

- lvl1 の連続加算は約 12.7% 短縮し、この測定では減算より軽くなった。
- lvl3 の連続加算は約 2.9% 短縮し、減算との差は約 1% になった。
- lvl5 の独立入力の加算は約 3.6% 短縮した。連続加算は約 0.8% 遅く、改善は確認できなかった。
- 独立入力の加算は、変更後も減算より約 5–6% 重い。Fp2 乗算全体の時間はほぼ同じだった。署名全体の高速化率として解釈しない。

同じ引数を繰り返すだけの計測は避け、64 組の入力を切り替えている。連続計算は `r = r + b[i]` の形。変更前後の計算結果も照合する。時間とソースの SHA-256 は [測定 JSON](fp-add-fusion-results.json) に保存した。

```sh
python3 scripts/gen_fp_backend.py --check
python3 scripts/test_fp_backend.py --repetitions 1000
python3 scripts/bench_fp_add.py --baseline /path/to/before-add-fusion --output /tmp/fp-add.json
```

`--baseline` には、52/55/57-bit の内部表現を使用し、今回の加算変更前のソースツリーを指定する。古い 64-bit 飽和表現とはこのスクリプトで比較しない。

**検証**

Python 整数オラクルに、和が 2p の前後となる入力や、limb 境界をまたぐ carry/borrow を狙った入力を追加した。各 1,000 個の乱数・境界値で、出力の範囲、mod 2p の正確な値、出力と各入力の重なりを確認する。全レベルでこの検証と UndefinedBehaviorSanitizer の検証が成功した。GCC の `fp_add` の逆アセンブルにはジャンプ命令がないことも確認した。これは対象コンパイラでの確認であり、あらゆる環境の定数時間性を保証するものではない。

全レベルの Fp/Fp2 テストと鍵生成・署名・検証各 100 回（計 9 テスト）も成功した。AddressSanitizer では Fp/Fp2 の 6 テストが成功した（漏洩検査は対象外）。
